1. Executive Summary
Bed of Roses is an open-source, AI-native operating system where artificial intelligence is not a feature — it is the entire interface. The OS boots into an empty canvas with a personalized AI companion (represented as a customizable animated avatar). Users interact with their computer through natural conversation, and the AI generates the entire user interface on the fly.
There are no pre-installed apps. No app store. No menus. The user talks, and the AI builds. Over time, the desktop organically fills with purpose-built widgets tailored to how each individual actually uses their computer. Through a dreaming and memory system inspired by Anthropic’s recent research, the AI consolidates what it learns between sessions, becoming progressively more useful without any changes to the underlying model.
The project’s philosophy: your operating system should grow with you, like a garden — not be handed to you fully built like a skyscraper.
2. Project Vision &amp; Philosophy
2.1 The Problem with Traditional Operating Systems
Every major OS today ships with hundreds of pre-built applications, settings panels, and interface paradigms that most users never touch. The user is expected to learn the OS’s language — where settings live, how file explorers work, what keyboard shortcuts do. The OS is a static product that barely adapts to individual usage patterns.
2.2 The Bed of Roses Approach
Bed of Roses inverts this relationship. Instead of the user learning the OS, the OS learns the user. The core principles are:
AI-First Interface: The primary interaction model is conversation, not clicks.
Emergent UI: Every interface element is generated by the AI based on user needs, not pre-designed by developers.
Organic Growth: The desktop starts empty and fills up naturally based on actual usage patterns.
Provider Agnostic: Users choose their own LLM provider (OpenAI, Anthropic, Google, local models, etc.).
Open Source: Fully transparent, community-driven, and free.
2.3 What “Bed of Roses” Means
The name reflects the aspiration: an operating system that feels effortless, personal, and beautiful — one that blooms around you. But also an acknowledgment that building something this ambitious won’t always be easy. Every rose has its thorns.
3. Core Architecture
3.1 System Overview
The OS is structured in five distinct layers, each with clear responsibilities:
Layer
Component
Responsibility
Layer 0
Base OS (Linux)
Hardware management, boot, kernel, drivers, filesystem
Layer 1
Display Shell
Chromium in kiosk mode — renders the entire UI as a web application
Layer 2
System Bridge
Node.js / Rust daemon providing system-level access (files, network, hardware)
Layer 3

Layer 4
Widget Runtime
Sandboxed iframe containers that host generated HTML/CSS/JS widgets
3.2 Layer 0: Base OS
The foundation is a minimal Linux distribution (Debian-based or Alpine) stripped to essentials. It provides the kernel and hardware abstraction, a filesystem for user data, widget storage, and memory files, networking stack, and audio/video subsystems. The OS boots directly into the Chromium shell with no traditional desktop environment (no GNOME, KDE, etc.).
3.3 Layer 1: Display Shell
Chromium runs in kiosk mode as the sole graphical interface. This choice gives us a battle-tested rendering engine for HTML/CSS/JS, GPU-accelerated graphics, built-in DevTools for power users who want to inspect widgets, Web APIs for audio, video, notifications, and more, and cross-platform consistency (same rendering on desktop and mobile via webview).
3.4 Layer 2: System Bridge
A backend daemon (Node.js for speed of development, with potential Rust rewrite for performance-critical paths) exposes system capabilities to the web frontend via a secure WebSocket or IPC channel. Capabilities include file read/write operations, system settings (volume, brightness, network), process management, hardware info (battery, CPU, memory), and API proxy (all external API calls route through the bridge for security).
3.5 Layer 3: AI Core
The brain of the OS. This layer manages conversation state and history, LLM API communication (supporting multiple providers), the structured output protocol (determining whether AI output is chat, a widget, a command, or a setting change), memory and dreaming systems, and context injection (user profile, widget registry, playbooks).
3.6 Layer 4: Widget Runtime
Each widget runs in an isolated sandboxed iframe with a strict Content Security Policy. Widgets communicate with the OS shell exclusively through a controlled postMessage bridge. This ensures that no widget can access another widget’s data, crash the main OS interface, or make unauthorized network requests.

5. User Experience &amp; Onboarding Flow
The onboarding experience is the most critical moment in the user’s relationship with Bed of Roses. It must accomplish three things: establish an emotional connection with the AI companion, configure the technical requirements (LLM providers), and demonstrate the core interaction loop (talk → AI builds → widget appears).
5.1 Step 1: Welcome Splash Screen
Trigger: First boot / initial setup.
The user sees a beautifully animated splash screen featuring the Bed of Roses logo — a stylized rose unfolding. This is analogous to the Apple logo appearing when you first power on an iPhone. Behind the scenes, this screen serves a functional purpose: loading system resources, initializing the Chromium shell, preparing the filesystem, and setting up the system bridge. A subtle progress indicator (petals opening, a growing vine, etc.) gives feedback without feeling technical. Duration: 3–5 seconds.
5.2 Step 2: Meet Your AI — Name &amp; Personality
Trigger: Splash screen completes.
The screen transitions to a friendly, inviting setup wizard. This is a multi-step process presented as a conversation, not a form:
Name Your AI: The user types a name for their AI companion (e.g., “Rosy,” “Atlas,” “Jarvis”). This name persists everywhere in the OS.
Choose an Avatar (Memoji-Style): The user customizes a cartoon avatar for their AI — selecting face shape, eyes, color palette, accessories, expressions. This avatar becomes the floating head on the homepage. The customization should feel playful and personal, like Apple’s Memoji or Bitmoji creation flow.
Select a Voice: The user can pick from pre-built voice options OR record a short sample that the AI will attempt to match (using voice cloning APIs if a voice provider is configured). The AI will use this voice for all spoken interactions. If no voice provider is configured, the OS falls back to browser-native TTS.
Personality Traits (Optional): The user can adjust sliders or pick traits like “formal vs. casual,” “verbose vs. concise,” “humorous vs. serious.” These map to system prompt modifiers.
5.3 Step 3: LLM Provider Setup
Trigger: Avatar setup completes.
A clean, guided setup screen where the user configures their AI’s “brain.” Three sections:
Text LLM Provider (Required)
This is the core intelligence. The user selects from supported providers (OpenAI, Anthropic, Google, Mistral, Groq, local/Ollama, etc.), enters their API key, and selects a model. The OS validates the key with a test call and shows a success animation (the avatar “wakes up”).
Image Generation Provider (Optional)
For wallpaper generation, widget illustrations, avatar enhancements. Options include DALL-E, Stable Diffusion (local or API), Midjourney API, etc. If skipped, the OS uses placeholder visuals and free image APIs.
Voice Provider (Optional)
For text-to-speech with the custom voice selected earlier. Options include ElevenLabs, OpenAI TTS, Google Cloud TTS, or local models. If skipped, browser-native speech synthesis is used.
5.4 Step 4: The Homepage — Your Blank Canvas
Trigger: LLM setup completes and validates.
The setup wizard fades away and the user arrives at their homepage for the first time. What they see:
A clean, empty screen (the wallpaper can be a subtle gradient or solid color for now).
Their customized AI avatar floating as an animated head in the center of the screen. The avatar is expressive — it blinks, looks around gently, and reacts to interactions.
A simple chat input field at the bottom of the screen, with a microphone button for voice input.
A subtle greeting in a chat bubble from the avatar: “Hey! I’m [Name]. This is our space — tell me what you need and I’ll start building.”
This is the core interaction surface. It is intentionally minimal. The emptiness is a feature, not a bug — it communicates that everything here will be built by and for the user.
5.5 Step 5: First Interaction — The “Aha Moment”
The user types or speaks their first request. For example: “Show me the latest flight prices from Lagos to London.”
What happens:
The avatar animates a “thinking” expression (eyes looking up, subtle pulse).
The AI processes the request, determines it needs to build a widget, and generates HTML/CSS/JS.
A widget card materializes on the screen with a smooth animation — sliding up from below or fading in.
The widget is automatically given a name (e.g., “Flight Tracker”), an auto-generated icon, and is saved to the homepage tile grid.
The avatar slides from the center of the screen to the top-right corner (its resting position when the homepage has content), making room for the widget.
The avatar says: “Here you go! I’ve saved this as a widget so you can check it anytime. What else do you need?”
This moment — watching the AI build a functional UI in real-time — is the core product experience. It must feel magical.
5.6 Ongoing Usage: The Growing Desktop
As the user continues interacting, more widgets populate the tile grid. The homepage evolves from an empty canvas into a personalized dashboard. The avatar remains accessible in the top-right corner and can be tapped/clicked to open the chat input. Key behaviors:
Widgets tile in a responsive grid (adapting to screen size — critical for mobile).
Users can long-press/right-click widgets to rename, edit (with AI assistance or raw code), resize, reposition, or delete them.
The AI proactively suggests new widgets based on usage patterns (powered by the dreaming system).
Wallpapers, themes, and visual customizations are generated on demand via conversation (“Make my background a sunset over mountains”).

7. Widget System
7.1 Widget Lifecycle
Creation: User requests something → AI generates HTML/CSS/JS → Code passes validation → Widget rendered in sandboxed iframe.
Naming: The AI auto-generates a descriptive name and icon for each widget.
Storage: The widget’s HTML is saved as a self-contained file in the widget directory.
Display: Widgets appear as tiles on the homepage grid. Each tile shows the widget name, icon, and a live preview.
Interaction: Users tap to expand a widget to full view, or interact with it inline if the tile supports it.
Editing: Users can ask the AI to modify a widget, or open the raw HTML in a built-in code editor.
Deletion: Users can remove widgets. The memory system notes what was deleted and why (if stated).
7.2 Widget Storage Structure
Each widget is stored as a self-contained directory:
/os-data/widgets/flight-tracker-001/
widget.html — The complete HTML/CSS/JS (single file, no external deps)
manifest.json — Name, icon, creation date, last modified, usage count, source prompt
state.json — Persistent state (user inputs, cached data, preferences)
thumbnail.png — Auto-generated screenshot for the tile grid
7.3 Widget Editing
Users have two paths to edit widgets:
AI-Assisted: The user tells the AI what to change (“Make the flight tracker show prices in Naira instead of dollars”). The AI modifies the HTML and the widget updates live.
Manual/Code: Power users can open the widget’s HTML in a built-in code editor (Monaco-based, like VS Code). Changes are saved and rendered immediately. The AI can be asked to explain the code or suggest improvements.
7.4 Tiling Layout System
Widgets are arranged in a responsive tile grid. This layout was chosen for its clean organization, mobile-friendliness, and the natural way it accommodates growth from 1 widget to 100. The grid adapts to screen size: 2 columns on mobile, 3–4 on tablets, 4–6 on desktop. Widgets can be resized to span multiple grid cells (1x1, 2x1, 2x2, etc.). Users can drag to reorder. The AI can suggest optimal layouts based on usage frequency (“You open Weather every morning — want me to move it to the top?”).
8. Memory &amp; Dreaming Architecture
This is the system that makes Bed of Roses genuinely improve over time. Inspired by Anthropic’s recently announced “Dreaming” feature for Claude Managed Agents, this architecture implements a two-tier memory system: active session memory and passive dream consolidation.
8.1 Active Memory (Session-Level)
During every interaction, the OS records what the user asked for, what widget was generated and whether it was used again, explicit preferences stated by the user, errors encountered and how they were resolved, and commands executed and their outcomes.
This raw data is stored as JSONL files in the sessions directory — one file per session.
8.2 Dreaming (Between-Session Consolidation)
Inspired by Anthropic’s dreaming system, this process runs when the OS is idle (screen locked, overnight, or on-demand). It is modeled after human REM sleep: consolidating important memories, pruning noise, and strengthening patterns.
The Dream Cycle runs in three phases:
Phase 1: Orient
The system reads the current user profile, widget registry, existing playbooks, and recent session logs. It builds a snapshot of “what the OS knows right now.”
Phase 2: Consolidate
The accumulated session data is sent to the LLM with a dream prompt. The AI analyzes patterns across sessions, identifying recurring requests and behaviors, widgets that are frequently used vs. ignored, preferences that have been stated or can be inferred, errors that keep happening, and workflow patterns (e.g., “user always checks weather, then opens email, then checks todo list”). The AI then produces a consolidated, deduplicated, prioritized memory — removing stale information and resolving contradictions.
Phase 3: Output
The dream cycle outputs updated versions of the user profile (preferences, habits, personality traits inferred), playbooks (learned workflows the AI can proactively suggest), widget recommendations (new widgets to offer based on observed needs), and system prompt modifiers (adjustments to how the AI communicates). All outputs are human-readable files that the user can inspect and modify. Nothing is hidden.
8.3 Dream Triggers
The dream cycle activates automatically when 24 or more hours have passed since the last dream, when 5 or more sessions have occurred since the last dream, or when the user explicitly asks the AI to “learn from my usage” or “update your memory.”
8.4 Memory File Structure
All memory is stored in a structured, human-readable directory:
/os-data/memory/
sessions/ — Raw session logs (JSONL, one per session)
user_profile.json — Consolidated user preferences and patterns
playbooks.md — Learned workflows and routines
widget_registry.json — Inventory of all widgets with usage statistics
dreams/ — Dream cycle outputs (auditable, timestamped)
embeddings.db — SQLite database with vector embeddings for semantic search
8.5 Semantic Memory Recall
For fast, relevant memory retrieval, the OS maintains a local embedding database. When the user makes a request, the system generates an embedding of the query and searches the memory store for semantically similar past interactions. This allows the AI to recall relevant context even when the user doesn’t explicitly reference it. For example, if a user says “plan another trip like last time,” the semantic search retrieves the previous travel planning session and its parameters.
9. Security Model
Because the AI can generate code, execute system commands, and access the network, security is paramount. Bed of Roses implements a five-layer defense architecture.
9.1 Layer 1: Permission Tiers
Every system action is categorized into permission tiers:
Tier
Actions
Gate
T0 — Free
Generate UI, answer questions, read preferences
None — always allowed
T1 — Notify
Create/save widget, call public API, change wallpaper
Toast notification shown
T2 — Confirm
Access files, install API integration, modify settings
User confirmation dialog
T3 — Protected
Delete data, access keys, shell commands, unknown network
Confirmation + PIN/biometric
The AI never directly executes T2 or T3 actions. It proposes them, and a system-level handler (completely separate from the LLM) enforces the gate.
9.2 Layer 2: Widget Sandboxing
Every widget runs in an iframe with strict Content Security Policy. Widgets cannot access the parent DOM, read cookies or storage from other widgets, make network requests to non-whitelisted domains, or execute code outside their sandbox. All widget-to-OS communication goes through a controlled postMessage bridge with a defined schema.
9.3 Layer 3: Code Validation
Before any AI-generated code is rendered, it passes through a static analysis validator that blocks dangerous patterns: eval(), Function(), document.cookie access, XMLHttpRequest to unknown domains, attempts to access the parent frame, script tags loading external resources, and any access to localStorage outside the widget’s scoped storage.
9.4 Layer 4: Prompt Injection Defense
The system architecture separates the instruction channel (user typing into the chat) from the data channel (content inside widgets, API responses, files). The LLM’s system prompt explicitly instructs it to only take actions from the instruction channel. Any instructions found inside data are flagged and ignored.
9.5 Layer 5: Audit Log
Every action the AI takes is logged immutably with timestamps, action type, permission tier, prompt and output hashes, and user approval status. Users can review the full audit trail through a built-in “History” view accessible from the settings.

11. Offline Capabilities
Bed of Roses follows a hybrid online/offline model. When the LLM API is unavailable:
What Still Works
All previously created widgets remain functional and interactive.
Cached data within widgets (last-fetched weather, saved tasks, etc.) is accessible.
Users can rearrange, resize, and manage existing widgets.
The audit log and settings remain accessible.
Saved playbooks and memory files can be viewed.
What Requires Connectivity
Creating new widgets (requires LLM).
AI conversation (requires LLM).
Widgets that fetch live data (weather, news, etc.).
Dream cycles (require LLM for consolidation).
Voice interaction with AI voice providers.
The avatar displays a “sleeping” or “offline” state with a clear indicator that the AI brain is unavailable, and a retry mechanism that auto-reconnects when connectivity returns.
12. Mobile Strategy
The tiling grid layout was chosen specifically for cross-platform support. On mobile devices, the same web-based UI renders in a mobile webview with these adaptations:
The tile grid collapses to 2 columns on small screens.
The avatar rests at the top of the screen rather than top-right.
The chat input is always at the bottom, matching mobile messaging conventions.
Widgets expand to full-screen when tapped (rather than expanding in-grid).
Swipe gestures navigate between widget pages.
Voice input is prioritized over typing on mobile.
For mobile distribution, the OS can be packaged as a PWA (Progressive Web App) initially, with native wrappers (Capacitor/Tauri Mobile) for app store distribution later.
13. MVP Scope &amp; Roadmap
13.1 Phase 1: Proof of Concept (Weeks 1–4)
Goal: Demonstrate the core loop — talk to AI, AI builds widget, widget appears on screen.
Static HTML page with the avatar (simple animated SVG/CSS), chat input, and widget grid.
Integration with one LLM provider (OpenAI or Anthropic).
AI can generate simple HTML widgets from conversation.
Widgets render in iframes on the homepage.
Basic widget persistence (saved to localStorage or filesystem).
13.2 Phase 2: Core OS (Weeks 5–12)
Goal: Build the foundational systems.
Multi-provider LLM support.
Full onboarding flow (splash → avatar → LLM setup → homepage).
Widget editing (AI-assisted + code editor).
Session memory and basic user profile.
Permission tier system (T0–T3).
System bridge for file access and settings.
Free API integration (weather, news, etc.).
13.3 Phase 3: Intelligence (Weeks 13–20)
Goal: Make the OS genuinely learn and improve.
Dream cycle implementation.
Semantic memory with local embeddings.
Playbook generation and proactive suggestions.
Widget usage analytics feeding into memory.
Voice interaction (STT + TTS).
Image generation for wallpapers and widget visuals.
13.4 Phase 4: Polish &amp; Distribution (Weeks 21–30)
Goal: Make it real.
Bootable Linux ISO with Chromium kiosk.
Mobile PWA / native wrapper.
Community widget marketplace (share widgets as HTML files).
Comprehensive security audit.
Documentation and contributor guides.
Public beta launch.
